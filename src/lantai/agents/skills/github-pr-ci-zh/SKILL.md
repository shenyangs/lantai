# GitHub PR 与 CI

把 Issue、代码变更、评审和 CI 当成一条可追溯交付链。默认先读取；提交、推送、创建/修改 PR、回复评论、重跑检查和合并都是外部写操作，必须在用户授权范围内执行。

## 1. 探测环境

先确认仓库、当前分支、工作区改动和仓库级说明。再运行 `gh --version` 与 `gh auth status`；不得输出 token、Cookie 或认证头。

- `gh` 可用且已认证：优先用它读取 Issue、PR、评论和 checks；
- `gh` 缺失：使用已配置的 GitHub 连接器或浏览器只读查看；
- 两者都不可用：报告缺失能力并给出可复制步骤，不静默安装。

安装与常用只读/写入命令边界见 [command-matrix.md](references/command-matrix.md)。

## 2. 建立交付合同

确认 Issue/PR 编号、目标分支、验收标准、禁止修改范围、测试要求、是否允许提交/推送/开 PR，以及 CI 等待截止点。读取仓库贡献规则和 PR 模板；不要仅凭 Issue 标题改代码。

工作区已有改动默认属于用户。区分本任务改动与既有改动，不覆盖、不清理、不把无关文件带入提交。

## 3. 实现与本地验证

1. 复现或确认当前行为；
2. 做满足验收标准的最小改动；
3. 运行与风险相称的测试、类型检查、lint 和构建；
4. 审阅 diff，检查秘密、生成物、调试代码和意外范围；
5. 把每项验收标准映射到代码与验证证据。

未经用户明确要求，不自动提交、推送或重写历史；禁止 `reset --hard`、强推和清理未知文件。

## 4. PR 与评审闭环

得到外部写授权后：

1. 只暂存本任务文件，形成意图明确的提交；
2. 推送当前任务分支，创建或更新 PR；
3. PR 正文写问题、方案、测试、风险和回滚；
4. 逐条读取未解决评审意见，区分必须修改、需要澄清和不采纳；
5. 修改后重新验证，在评论中给出证据，不用空泛的“已修复”；
6. 监控 required checks，失败时读取具体 job/step 日志，先判断代码失败、测试不稳定、配置问题还是基础设施问题。

重跑 CI、关闭对话、请求评审和合并均会改变 GitHub 状态；只有明确授权时执行。不得为了变绿而跳过测试、降低门禁或修改无关检查。

## 输出

- Issue/PR 与验收标准摘要；
- 修改文件及范围；
- 本地验证结果；
- 评审意见处置表；
- checks 的通过、失败、等待和未运行项；
- 已执行的 GitHub 写操作；
- 剩余风险、阻塞和下一步。

## 完成定义

验收标准均有实现或明确阻塞，diff 不混入无关改动，关键验证实际执行，评审意见有证据化处置，required checks 状态清楚，且没有未经授权的推送、评论、重跑或合并。
