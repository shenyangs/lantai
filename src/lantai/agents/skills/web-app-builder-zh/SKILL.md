# Web 应用交付

使用澜台原生文件、Shell 与浏览器工具完成 `plan → design → implement → verify → package`。不依赖 AppBase、Comate 或任何特定云平台。

## 1. 计划

1. 读取仓库规则、现有结构、依赖和未提交改动。
2. 把请求写成可观察的验收条件：入口、关键流程、数据状态、响应式范围和交付形式。
3. 优先沿用现有技术栈。不要为了单页任务引入新框架。
4. 标记外部写入、部署、账号、支付和删除等需要用户授权的动作。

## 2. 设计

先确定信息层级、页面骨架、交互状态和视觉系统，再写组件。已有品牌或截图时从证据中提取规则；没有时采用克制、清晰、可访问的默认设计。

读取：

- [visual-system.md](references/visual-system.md)：需要新设计、重设计或从截图还原时。
- [product-patterns.md](references/product-patterns.md)：需要为常见产品类型选择结构和视觉方向时。
- [quality-gates.md](references/quality-gates.md)：实现和交付前必须读取。

## 3. 实现

- 使用 `rg`、`read_file` 理解现有实现；使用 `apply_patch` 做范围明确的修改。
- 保留既有 API、路由、配置和持久化契约，除非任务明确要求改变。
- 组件覆盖加载、空态、错误、禁用和成功状态。
- 不把密钥、用户数据或内部推理写进前端包。
- 没有真实后端时使用显式标注的本地样例数据，不伪造线上成功。

## 4. 验证

1. 运行项目已有 lint、类型检查、单测和构建。
2. 用澜台浏览器打开实际页面，检查核心路径、控制台错误、窄屏和宽屏。
3. 对视觉重要页面保存截图；对复杂交互记录复现步骤。
4. 失败时先定位根因，再做最小修复并重跑相关验证。

## 5. 交付

- 交付可运行入口，而不是孤立代码片段。
- 说明改动范围、验证结果、已知限制和需要用户完成的外部步骤。
- 除非用户明确要求，不自动部署、不创建账号、不发布到外部服务。

## 停止条件

验收条件全部通过、页面可实际打开、关键交互有证据、没有未说明的模拟数据或失败验证。
