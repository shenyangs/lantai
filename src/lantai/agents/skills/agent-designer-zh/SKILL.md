# Agent 设计器

把 Agent 设计成一个边界清楚、可以验证、能够安全失败的执行角色，而不是一段宽泛人设。

## 1. 先判定是否需要新 Agent

只有在工作会重复出现、角色边界稳定、需要独立上下文或权限、且现有 Agent 加一个 Skill 仍不足时，才新建 Agent。一次性调查、单一方法复用或简单自动提醒，分别优先使用当前 Agent、Skill 或自动化。

先检查现有角色模板、Agent 和 Skill，给出“扩展现有 / 新建 / 不创建”的结论，避免重名和职责重叠。

## 2. 建立设计合同

在改配置前明确：

- 用户时刻：谁在什么情况下会把什么任务交给它；
- 使命与非目标：必须完成什么，明确不做什么；
- 输入、输出、停止条件和失败返回；
- 模型选择及降级路径；
- 所需 Skill、内置工具、MCP 工具和最小工具白名单；
- 工作区资料、短期上下文、长期记忆及写回条件；
- 外部写入、发布、删除、付款、消息发送等确认点；
- 可观测证据、成本/延迟边界和评测集。

需要完整字段和验收样例时读取 [evaluation.md](references/evaluation.md)。

## 3. 形成最小配置

优先从最接近的内置角色模板开始，只加入完成使命必需的能力。不要为“以后可能用到”开放全部 Skill、全部 MCP 工具或长期记忆写入。

可用路径：

- 图形界面：设置中的 Agent 管理和角色模板；
- 命令行：先运行 `lantai agents --help` 与 `lantai agents create --help` 探测可用参数；
- 创建命令支持 `--name`、`--agent-id`、`--description`、`--workspace-dir`、`--language`、`--template`、重复的 `--skill`，以及成对的 `--provider-id` / `--model-id`。

命令行不可用时，回退到图形界面；两者都不可用时只交付 Agent 规格，不猜测配置路径，也不静默安装依赖。

## 4. 先评测再扩权

1. 用 3 个核心任务验证主路径。
2. 用 3 个相邻任务验证不会误接单。
3. 用缺失资料、工具不可用、模型失败验证降级。
4. 用越权请求验证确认点和拒绝路径。
5. 检查输出能否追溯到输入、工具结果和明确推断。
6. 只在证据显示能力不足时增加 Skill、工具或权限。

## 5. 变更与交付

默认先提交规格和差异预览。只有用户明确要求创建或修改时才写 Agent 配置；删除 Agent、删除工作区、打开外部写权限或更换带来显著成本/隐私变化的模型必须单独确认。

交付包括：设计取舍、最终规格、实际变更、正负评测结果、剩余风险和回滚方式。

## 完成定义

职责不与现有角色冲突，配置采用最小能力集合，核心/负向/失败/权限评测均有结果，外部副作用受确认点保护，且 Agent 可以在明确条件下停止或安全失败。
