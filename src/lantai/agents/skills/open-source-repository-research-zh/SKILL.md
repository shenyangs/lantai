# 开源仓库研究

目标是回答“它真正怎么工作，我们应该借什么”，而不是用 README、Star 数或一张架构图冒充源码研究。

## 先定义调研合同

记录仓库 URL、分支/标签/提交、检索时间、用户的真正决策和停止条件。选择最小充分深度：

- **快速**：判断是什么、怎么跑、值不值得继续研究；
- **标准**：还原入口、主流程、数据流、依赖和可借鉴机制；
- **深入**：追关键调用链、状态机、错误恢复、测试/发布约束与安全边界；
- **对比**：对 2–4 个候选使用同一决策问题和证据口径。

## 安全取证

1. 优先固定到 tag 或 commit；记录最终研究的 revision。
2. 默认只读 README、文档、manifest/lockfile、入口、核心模块、测试、CI、发布与许可证。
3. 需要本地检索时使用临时目录浅克隆，不把外部仓库混入当前项目。
4. 未人工审核前，不运行安装脚本、构建脚本、仓库二进制、容器、hook 或未知程序。
5. 不猜测隐藏路径，不枚举用户数据，不绕过登录、付费墙或其他访问控制。

当只能看到公开网页、静态 JS 或客户端 API 契约时，必须将“已观察到的客户端行为”与“未取得的服务端实现”分开，不得声称已掌握后端源码。

## 源码级工作流

1. **建地图**：列顶层目录、语言、构建系统、运行入口、数据存储、外部服务和产物边界。
2. **找主链**：从一个用户可见动作出发，追到入口、编排、核心模块、持久化/外部调用与最终产物。
3. **找合同**：识别 schema、事件、队列、状态机、文件格式、可插拔接口和版本边界。
4. **找反例**：阅读失败路径、重试、幂等、恢复、降级和未完成状态，不只画 happy path。
5. **核工程证据**：用测试、fixture、CI、release note、issue/PR 和提交历史验证自述。
6. **判断借鉴方式**：在“直接依赖”“适配一个边界”“只借设计模式并独立实现”“不采用”中选一个。

评审项和对比口径见 [research-rubric.md](references/research-rubric.md)。

## 对比模式

不使用固定“性能 25%”一类通用权重。先从真实任务中定义 3–7 个硬约束和判断维度，再对每个候选使用同等深度的一手证据。维度可包括：与现有架构的贴合度、可撤回成本、运行时依赖、发布风险、维护活性、许可证、安全和可观测性。

若问题超出公开仓库范围，先用本 Skill 建立候选证据，再交给“案头研究”补资料、“美式”完成最终决策，不在本 Skill 里复制一整套泛化战略流程。

## 交付合同

先给一句话判断，再交付：

- 仓库快照：固定版本、许可证、活性与核心依赖；
- 机制图：主链、状态/数据流、错误恢复；
- 关键文件表：路径、职责、支撑的主张和限制；
- 事实/推断/未知：尤其标明没有取得的服务端、模型、数据或内部运维实现；
- 采用决策：借什么、不借什么、许可/安全边界、最小可逆试验和退出条件。

## 停止条件

用户的决策问题已回答；关键主张可追溯到文件、提交或官方资料；未取得部分已标未知；借鉴建议有许可与安全边界；下一步是可逆小试验或明确不做。
