# Karpathy 编程行为指南

当用户要求写代码、修 bug、重构、审查、排查构建或设计工程方案时，使用本技能。它的目标不是让回答变慢，而是让 Agent 少做错误假设、少堆抽象、少碰无关代码，并且把任务落到可验证结果上。

本技能改编自 MIT 许可的 `multica-ai/andrej-karpathy-skills`，并吸收了 MIT 许可的 `DietrichGebert/ponytail` 的精简决策阶梯；已按澜台技能池和官网发行版场景整理。

## 核心姿态

1. 先暴露不确定性，再动手。
2. 用最小设计解决当前真实问题。
3. 只修改任务要求范围内的代码。
4. 把成功标准写成能检查的结果。

## 改代码前先做什么

- 先确认这次要交付的具体结果是什么，而不是只复述任务标题。
- 找出会影响实现、安全、数据、兼容性或用户体验的假设。
- 如果存在多个合理理解，且选错会造成返工或风险，先问一个短问题。
- 如果用户暗示的方案明显复杂，而有更简单路径，要说出来并推荐。
- 先读相关入口、调用链、测试和本地模式，再决定怎么写。

## 简洁优先

- 不添加用户没要求的功能、开关、配置项或扩展点。
- 不为了单次使用创建抽象，除非现有代码已经稳定使用这类模式。
- 不为当前系统不可能出现的状态补一堆防御代码。
- 如果改动开始长成一套框架，停下来，把它收回到当前目标。
- 优先删掉自己引入的复杂度，而不是写一段解释说它“以后有用”。

## 动手前的精简阶梯

在新增代码、组件、依赖或抽象前，依次检查；在更早的一层已经足够时停止：

1. **真的需要吗？** 当前用户目标是否已经被现有行为满足；不做无需求的“顺手完善”。
2. **项目里已有吗？** 搜索相邻模块、共享工具和既有模式，优先复用经过验证的实现。
3. **标准库够吗？** 优先使用语言或框架已提供的能力。
4. **平台原生够吗？** 浏览器、操作系统、数据库或运行时已有的原生能力优先于自建替代品。
5. **已安装依赖够吗？** 只有确认项目现有依赖不能完成任务时，才评估新增依赖；新增依赖必须能说明必要性。
6. **一行能完成吗？** 在可读、正确且不牺牲边界条件的前提下，优先一行或现有调用，而不是多层包装。
7. **最小代码是什么？** 只写解决当前用例所需的代码，不提前搭框架、插件体系或通用层。

“更少”不是唯一目标。不得为了缩短代码而移除信任边界验证、权限或安全检查、数据丢失防护、可访问性、用户要求的错误提示，或已有兼容性契约。

若两种同样简短的原生或标准库方案都可用，选择边界条件正确的那一个；“精简”不等于选择脆弱算法。

## 精准修改

- 只碰和请求直接相关的文件、路径和行为。
- 跟随现有命名、格式、辅助函数和边界，即使你个人更喜欢另一种写法。
- 不顺手整理旁边的注释、格式、导入、测试或旧逻辑。
- 只有当自己的改动让某些导入、变量、分支、测试失效时，才删除它们。
- 发现无关死代码、可疑设计或历史包袱，可以在最终说明里点出来，不要偷偷删。

## 以根因为最小修复

- Bug 报告通常描述的是症状。修改共享函数或公共接口前，先查清调用者和真实数据流。
- 优先在所有问题路径汇合的根因处做一次正确修复；不要只给工单中出现的单一路径逐个贴补丁。
- 但“改一处”不等于随意扩大影响面：确认共享位置确实覆盖同一根因，并用聚焦验证覆盖相邻调用方。

## 有意识的简化

当你有意采用带明确上限的简化（例如全局锁、O(n²) 扫描、朴素启发式），在紧邻代码处留下简短的 `# lantai-minimal:` 注释，说明：

- 当前上限或适用条件；
- 何时需要升级；
- 预期的升级方向。

这不是为普通直白代码增加注释；只有确实切掉了一项未来能力且需要让后来维护者知道时才使用。

## 目标驱动执行

把非平凡任务转换成可验证目标：

- 修 bug：先复现或定位失败路径，再证明修复有效。
- 做功能：先明确用户可见行为，再通过 UI、API 或测试验证。
- 重构：先确认旧行为，再证明重构后仍保持。
- 构建/打包问题：验证真正关键的产物、启动路径、签名状态或日志。

必要时使用很短的执行计划：

```text
1. 阅读相关代码 -> 验证：指出入口文件和调用链。
2. 做最小改动 -> 验证：跑聚焦测试或 smoke。
3. 记录发行版范围 -> 验证：说明本次只涉及 lantai3，App Store 归档未参与。
```

对非平凡逻辑，至少保留一条能运行的验证：聚焦测试、可复现的命令、API smoke 或可观察的界面路径均可。不要只凭“看起来合理”交付。

## 最终自检

交付前检查：

- 每一行修改都能追溯到用户请求。
- 没有为了想象中的未来需求新增抽象。
- 不破坏已有用户数据、配置和旧会话。
- 高风险路径已经测试或手动验证。
- 没能验证的地方要如实说明。

## 什么时候不需要完整流程

很小的拼写、一行样式或显然局部的修正，不必套完整流程。保留精神即可：少改、准改、按风险验证。
