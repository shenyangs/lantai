# Agent 运行诊断

先重建实际发生了什么，再解释为什么。默认只读诊断；用户只要求诊断时，不顺手修改配置、代码、数据或外部系统。

## 1. 固定诊断对象

记录 Agent、任务/会话/运行标识、发生时间、预期结果、实际症状、是否可复现、影响范围和用户已尝试的操作。没有唯一标识时，先从当前聊天的运行状态和调试信息中缩小到一条运行，不混合多个样本。

## 2. 按证据顺序取数

1. 当前聊天或运行调试中的最终状态与用户可见错误；
2. 运行事件、重放/轨迹、工具请求和工具结果；
3. 模型请求、首 token/总耗时、token 用量、重试与取消；
4. `lantai doctor --deep` 的 Agent、MCP、Skill、安全和内存检查；
5. 相关日志、固定 fixture 或最小复现。

只拿到导出的 JSON/JSONL 事件时，可运行：

```bash
python3 scripts/analyze_trace.py --input /path/to/events.jsonl
```

脚本只使用 Python 标准库，会汇总时间线、长间隔、错误、重复工具和终态；其结果是线索，不代替原始证据。详细分类读取 [diagnostic-rubric.md](references/diagnostic-rubric.md)。

## 3. 重建时间线

按时间排序并标记：接收请求、上下文组装、模型开始/结束、工具调用/返回、重试、人工审批、取消、终态。分别计算排队、模型、工具和审批等待，不能把总耗时全部归因于模型。

把每个结论绑定到具体事件或日志。对缺失事件、时钟不一致、被截断输出和无法取得的服务器侧信息明确标记未知。

## 4. 分层定位

依次排除输入/路由、上下文/记忆、模型、Skill、工具/MCP、权限/审批、编排/状态机、存储/网络和界面呈现。每个候选原因写出支持证据、反证和下一项最小验证。

只在一个假设能解释主要症状、时间线和复现结果，且关键替代解释已被排除时称为根因；否则报告“最可能原因”和置信度。

## 5. 划定修复边界

给出按风险排序的最小修复建议、验证方式和回滚点。用户随后明确要求修复时，再切换到对应实施或诊断开发流程；不要因为发现问题就自动重跑任务、改配置、清理状态或重发外部动作。

## 输出

- 症状与影响；
- 证据完整度；
- 带时间戳的关键时间线；
- 根因或候选原因、置信度、支持与反证；
- 最小复现；
- 建议修复、验证与回滚；
- 仍未知的部分。

## 完成定义

诊断对象唯一、证据来源可追溯、关键等待和重试已量化、原因没有越过证据、可用最小复现或后续验证区分主要假设，且诊断过程没有制造新的外部副作用。
